# Taskbar 2 – WebSocket Event Reference

This note documents every WebSocket event understood by the Go backend. Each
message uses the common envelope:

```json
{
  "event": "<event_name>",
  "data": <payload>
}
```

Unless stated otherwise all timestamps are serialized as RFC 3339 strings in UTC
and all identifiers are UUID strings.

Models returned by the server use the JSON representation generated by `sqlc`:

- `Task` – the fields defined in `internal/database/models.go` (`id`,
  `title`, `description`, `created_at`, `completed_at|null`, `duration`,
  `category`, `tags`, `toggled_at|null`, `is_active`, `is_completed`,
  `user_id`, `last_modified_at`, `priority|null`, `due_at|null`,
  `show_before_due_time|null`, `visible_from|null`).
- `Notification` – `id`, `user_id`, `title`, `description|null`, `status`,
  `notification_type`, `payload` (JSON object), `priority`, `expires_at|null`,
  `snoozed_until|null`, `action_url|null`, `action_text|null`, `created_at`,
  `updated_at`, `last_modified_at`, `seen_at|null`, `archived_at|null`.
- `Schedule` – `id`, `user_id`, `kind`, `title`, `tz`, `start_local`,
  `rrule|null`, `until_local|null`, `show_before_minutes|null`,
  `notify_offsets_min[]`, `muted_offsets_min[]`, `active`, `rev`,
  `last_materialized_until|null`, `created_at`, `updated_at`,
  `category|null`, `common_language|null`, `urgency`, `series_uuid`,
  `deleted_at|null`, `is_all_day`, `all_day_span_days`, `duration_minutes`,
  `description`, `tags[]`, `priority|null`, `due_offset_minutes|null`,
  `source_template_id|null`, `source_template_rev|null`,
  `source_template_variables|null`.
- `TaskTemplate` – `id`, `user_id`, `title`, `description`, `category`,
  `tags[]`, `priority|null`, `show_before_due_time`, `due_offset_minutes|null`,
  `variables` (JSON array of `{key,label?,description?,required}`), `rev`,
  `created_at`, `updated_at`, `last_modified_at`, `last_used_at|null`.

Null-able fields are emitted as `null` when the underlying value is not present.

For the dedicated task template contract, see
[`docs/frontend_task_templates_ws_contract.md`](./frontend_task_templates_ws_contract.md).

## Connection & Keep-alive

### `connect` (client → server)

Registers or authenticates a user session.

```json
{
  "event": "connect",
  "data": {
    "id": "<optional UUID – ignored>",
    "email": "john@example.com",
    "first_name": "John",
    "last_name": "Doe",
    "google_uid": "<Google UID – required>"
  }
}
```

- If the email is unknown the backend creates a new user record.
- If the email exists the `google_uid` must match the stored value.

**Success response:** `connected`

```json
{
  "event": "connected",
  "data": {
    "sid": "<connection UUID>",
    "id": "<user UUID>",
    "first_name": "John",
    "last_name": "Doe",
    "email": "john@example.com",
    "created_at": "...",
    "updated_at": "...",
    "categories": "<comma separated string or empty>",
    "key_commands": "<JSON string or empty>",
    "tasks": [<Task>, ...],
    "notifications": [<Notification>, ...],      // unseen by default
    "notifications_unseen_count": 3,
    "tags": ["work", "urgent"],
    "schedules": [<Schedule>, ...],              // active + inactive, excludes past one-offs
    "user_settings": {
      "calendar_filters": {
        "hidden_kinds": [],
        "hidden_states": [],
        "hidden_schedule_ids": []
      },
      "updated_at": "<RFC3339>"
    }
  }
}
```

**Failure response:** `connection_error`

```json
{
  "event": "connection_error",
  "data": {
    "type": "invalid_google_uid" | "google_uid_mismatch" | "user_creation_failed" | "database_error" | "invalid_data",
    "message": "<reason>",
    "code": 400 | 403 | 500
  }
}
```

### `ping` (server → client) / `pong` (client → server)

- The server emits `{"event":"ping","data":""}` every 5 s.  
- The client must answer with `{"event":"pong","data":{}}` (payload can be any JSON value).
- Missing a `pong` within 60 s closes the connection.

### `taskbar-update` (client → server)

Diagnostic hook. Emits `taskbar-ack` to every other session of the same user.

```json
{
  "event": "taskbar-update",
  "data": {}
}
```

**Response:** `taskbar-ack`

```json
{
  "event": "taskbar-ack",
  "data": "From <SID>"
}
```

## Task Events

All task mutations target the authenticated user inferred from the connection.

### `task_create` (client → server)

```json
{
  "event": "task_create",
  "data": {
    "id": "<uuid generated client side>",
    "title": "Write summary",
    "descripiton": "Markdown typo kept for compatibility",
    "created_at": "<RFC3339>",
    "completed_at": "<RFC3339>",            // required by backend; use epoch start if not completed
    "duration": "00:00:00",
    "category": "Work",
    "tags": ["writing"],
    "toggled_at": 0,
    "is_completed": false,
    "is_active": false,
    "last_modified_at": 1700000000000,      // epoch millis
    "priority": 1,                          // optional
    "due_at": "<RFC3339> | null",
    "show_before_due_time": 180             // minutes, optional
  }
}
```

- Stores the task using the provided `id`.
- `completed_at` is stored as nullable time; supply a sensible default when task is not yet completed.

**Broadcast (siblings only):** `new_task_created` with the persisted `Task`. The issuing client does not receive the echo; maintain local state optimistically.

### `task_toggle` (client → server)

```json
{
  "event": "task_toggle",
  "data": {
    "uuid": "<task id>",
    "toggled_at": 1700000000000,
    "is_active": true,
    "duration": "00:05:03",
    "last_modified_at": 1700000000001
  }
}
```

**Broadcast (others):** `related_task_toggled` with the updated `Task`.

### `task_edit` (client → server)

```json
{
  "event": "task_edit",
  "data": {
    "id": "<task id>",
    "title": "Write summary",
    "description": "Updated copy",
    "category": "Work",
    "tags": ["writing", "docs"],
    "last_modified_at": 1700000002222,
    "priority": 1,
    "due_at": "<RFC3339> | null",
    "show_before_due_time": 180
  }
}
```

**Broadcast (others):** `related_task_edited` with the updated `Task`.

### `task_completed` (client → server)

```json
{
  "event": "task_completed",
  "data": {
    "id": "<task id>",
    "completed_at": "<RFC3339>",
    "duration": "00:25:00",
    "tags": ["focus", "inbox"],
    "last_modified_at": 1700001111111
  }
}
```

- `tags` is optional; when omitted, existing tags remain unchanged.

- Marks the task complete and removes it from the active set.

- If `show_before_minutes` is set on a schedule, the server also schedules a task notification at `due_at - show_before_minutes` (in addition to any `notify_offsets_min` offsets).

**Broadcast (others):** `related_task_deleted` with `{ "id": "<task id>" }`.

- If the task has active linked list runs with incomplete required checklist
  items, the server rejects the mutation with `connection_error`:

```json
{
  "event": "connection_error",
  "data": {
    "type": "task_blocked_by_list",
    "message": "Task has incomplete required list items",
    "code": 409
  }
}
```

### `get_completed_tasks_v2` (client → server)

Enhanced completed task retrieval with multi-select categories, include/exclude tags, include/exclude keywords, and server-returned filter options.

> **Note:** `get_completed_tasks` (v1) remains available and unchanged. Use `get_completed_tasks_v2` for the richer filtering UI.

**Request:**

```json
{
  "event": "get_completed_tasks_v2",
  "data": {
    "categories": ["Work", "Errands"],
    "include_tags": ["focus", "deep-work"],
    "exclude_tags": ["blocked"],
    "include_keywords": ["report", "summary"],
    "exclude_keywords": ["draft"],
    "start_date": "2026-03-08T00:00:00Z",
    "end_date": "2026-03-08T23:59:59Z"
  }
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `categories` | `string[]` | No | Include-any: keep tasks whose category matches any entry (case-insensitive). Empty or omitted = no category filter. |
| `include_tags` | `string[]` | No | Include-any: keep tasks that have at least one tag matching any entry (case-insensitive). Empty or omitted = no include-tag filter. |
| `exclude_tags` | `string[]` | No | Exclude-any: remove tasks that have any tag matching any entry (case-insensitive). Empty or omitted = no exclude-tag filter. |
| `include_keywords` | `string[]` | No | Include-any: keep tasks where any keyword appears as a case-insensitive substring in `title`, `description`, `category`, or any `tag`. Empty or omitted = no include-keyword filter. |
| `exclude_keywords` | `string[]` | No | Exclude-any: remove tasks where any keyword appears in those same fields. Empty or omitted = no exclude-keyword filter. |
| `start_date` | `string` (RFC 3339) | No | Start of date range for `completed_at`. Defaults to start of current UTC day (`00:00:00`). |
| `end_date` | `string` (RFC 3339) | No | End of date range for `completed_at`. Defaults to end of current UTC day (`23:59:59`). Time component is always normalized to `23:59:59`. |

**All fields are optional.** Sending `{"data": {}}` returns all tasks completed today with no additional filtering.

**Filter semantics:**

- Filters are applied in order: categories → include tags → exclude tags → include keywords → exclude keywords.
- Include filters use **any-match**: a task passes if it matches **any** entry in the array.
- Exclude filters use **any-match removal**: a task is removed if it matches **any** entry in the array.
- All string comparisons are **case-insensitive**.
- Keywords use **substring matching** (e.g., keyword `"report"` matches title `"Write quarterly report"`).
- Input arrays are trimmed, deduplicated, and empty strings are dropped before filtering.

**Direct response:** `completed_tasks_v2`

```json
{
  "event": "completed_tasks_v2",
  "data": {
    "tasks": [
      {
        "id": "aaaaaaaa-0000-0000-0000-000000000001",
        "title": "Write quarterly report",
        "description": "Q1 summary for stakeholders",
        "created_at": "2026-03-08T09:00:00Z",
        "completed_at": {"Time": "2026-03-08T14:30:00Z", "Valid": true},
        "duration": "00:00:00",
        "category": "Work",
        "tags": ["focus", "deep-work"],
        "toggled_at": null,
        "is_active": false,
        "is_completed": true,
        "user_id": "11111111-2222-3333-4444-555555555555",
        "last_modified_at": 1741444200000,
        "priority": null,
        "due_at": null,
        "show_before_due_time": null,
        "visible_from": null
      }
    ],
    "available_filters": {
      "categories": ["Errands", "Home", "Work"],
      "tags": ["blocked", "deep-work", "focus", "quick"]
    }
  }
}
```

| Response field | Type | Description |
|----------------|------|-------------|
| `tasks` | `Task[]` | Filtered tasks matching all criteria. Standard `Task` model (same as v1). Empty array if no matches. |
| `available_filters.categories` | `string[]` | All distinct non-empty categories from completed tasks in the requested date range (sorted alphabetically). **Not affected by category/tag/keyword filters** — always reflects the full date range. |
| `available_filters.tags` | `string[]` | All distinct non-empty tags from completed tasks in the requested date range (sorted alphabetically). **Not affected by category/tag/keyword filters** — always reflects the full date range. |

**Broadcast scope:** Requesting session only (SendToClient).

**Error cases:** Returns a Go error (no `connection_error` event) if the client SID is not found or the database query fails.

## Frontend checklist

- **Initial load:** read `connected` payload for `tasks`, `notifications` (unseen), and `schedules`, then call `occurrences_fetch` for the visible calendar window.
- **Notifications paging:** call `notifications_fetch` with `offset`/`limit` (default 10, max 100) and append results on scroll.
- **Tab filters:** New = `statuses: ["unseen"]`; History = `statuses: ["seen"]`; Archived = `statuses: ["archived"]`; Snoozed = `only_snoozed: true` (optionally `include_snoozed: true`).
- **Realtime updates:** subscribe to `new_task_created`, `related_task_*`, `notification_created`, `notifications_marked_seen`, `notifications_reemitted`, `schedule_*`, `user_settings_updated`.
- **Template surfaces:** also subscribe to `template_created`, `template_updated`, `template_deleted`.
- **Push token lifecycle (mobile/web):** call `push_token_upsert` after login/connect and on token refresh; call `push_token_remove` on logout.

One of `snooze_until`, `snooze_minutes`, `snooze_seconds` must be supplied. If
the computed time is in the past the server enforces a minimum of 5 minutes.
If `urgency` is provided, the backend stores it in notification `payload.urgency`
and updates notification priority (`max`, `urgent`, and `ultimate` all map to
DB priority `urgent`). The payload keeps the supplied urgency label.

**Broadcasts:**

- `notification_snoozed` with the updated `Notification`.
- `notifications_unseen_count`.

### Server-initiated notification events

- `notification_created` – emitted when a scheduled notification job is
  dispatched. Payload is a `Notification`.
  - When `FCM_ENABLED=true`, the server also attempts FCM delivery for each active token of that user (best effort; DB notification creation remains source of truth).
- `notifications_reemitted` – produced when snoozed notifications become due:
  - When `FCM_ENABLED=true`, the server also attempts FCM delivery for each
    re-emitted notification (best effort; the existing notification row is
    reused rather than creating a new notification).

  ```json
  {
    "event": "notifications_reemitted",
    "data": {
      "notifications": [<Notification>, ...]
    }
  }
  ```

- `notifications_unseen_count` – broadcast after any change affecting unseen
  totals (creation, snooze release, mark-seen, archive).

## Schedule & Reminder Events

Field semantics follow the `Schedule` struct. `kind` must be either `task` or
`reminder`. `tz` is an IANA identifier.

When attaching a template, use:

```json
{
  "template_use": {
    "template_id": "<template id>",
    "template_rev": 3,
    "variables": {
      "name": "Alex"
    }
  }
}
```

- `template_use` is valid only for `kind = "task"`.
- `template_rev` must match the current template revision.
- variables marked `required=true` must be provided and non-blank.
- optional variables may be omitted or blank and render as empty strings.
- when a template is attached to a schedule, the backend copies rendered task
  content and rendered schedule-owned lists into the schedule snapshot; later
  template edits do not mutate that schedule.

### `schedule_create` (client → server)

```json
{
  "event": "schedule_create",
  "data": {
    "kind": "task" | "reminder",
    "title": "Daily stand-up",
    "tz": "Europe/Bucharest",
    "start_local": "<RFC3339>",          // local time
    "rrule": "FREQ=DAILY;INTERVAL=1",    // optional
    "until_local": "<RFC3339>",          // optional
    "show_before_minutes": 15,           // optional
    "notify_offsets_min": [2880,1440],   // optional, defaults applied when omitted
    "muted_offsets_min": [0],            // optional
    "category": "Work",                  // optional, defaults to "Life"
    "common_language": "every weekday at 9", // optional
    "urgency": "high",                   // optional, defaults to "normal"
    "is_all_day": false,                 // optional, defaults to false
    "all_day_span_days": 1,              // optional, defaults to 1
    "duration_minutes": 25,              // optional
    "template_use": null                 // optional, task schedules only
  }
}
```

- `title` is required unless `template_use` is provided.
- when `template_use` is present, the backend copies `title`, `description`,
  `category`, `tags`, `priority`, `show_before_minutes`,
  `due_offset_minutes`, template provenance, and rendered schedule-owned lists
  from the template snapshot.

**Response:** `schedule_created` with the persisted `Schedule`.

### `schedule_delete` (client → server)

```json
{
  "event": "schedule_delete",
  "data": {
    "id": "<schedule id>",
    "delete_mode": "schedule_only",
    "future_from": "2026-06-01T00:00:00Z"
  }
}
```

- `delete_mode` is optional (default `schedule_only`):
  - `schedule_only`: soft-delete schedule only.
  - `schedule_and_future_occurrences`: soft-delete schedule and delete future occurrences (`occurs_at > now`).
  - `schedule_and_future_occurrences_after_date`: soft-delete schedule and delete occurrences from a date (`occurs_at >= future_from`).
- `future_from` is required for `schedule_and_future_occurrences_after_date`.
- In all modes, future jobs are canceled before soft-delete.
- After soft-delete, `occurrences_fetch` still returns this schedule's past/current occurrences (`occurs_at <= server_now`) when they fall inside the requested window; future occurrences are excluded.

**Response:** `schedule_deleted` with `{ "id": "<schedule id>" }`.

### `reminder_submit` (client → server)

Used by the natural-language reminder flow.

```json
{
  "event": "reminder_submit",
  "data": {
    "title": "Call Alice",
    "kind": "reminder" | "task",
    "scheduleInput": "<original user input>",
    "schedule": {
      "instant": {
        "label": "today",
        "iso": "<RFC3339>"
      },
      "recurrence": null           // set when using parsed recurrence
    },
    "show_before_minutes": 0,
    "category": "Life",
    "urgency": "normal",
    "duration_minutes": 15,
    "template_use": null
  }
}
```

- Exactly one of `schedule.instant` or `schedule.recurrence` must be non-null.
- `schedule.instant.iso` and `schedule.recurrence.start` are parsed with
  `time.Parse` in RFC 3339 format.
- `title` is required unless `template_use` is provided.
- `template_use` is valid only for `kind = "task"`.
- when `template_use` is present, the created schedule stores a rendered copy
  of the template snapshot and rendered schedule-owned lists.

**Response:** `reminder_submit_response`

```json
{
  "event": "reminder_submit_response",
  "data": {
    "success": true,
    "schedule": <Schedule>
  }
}
```

If the instant reminder is due within two minutes, the server immediately
creates the first occurrence and may emit:

- `new_task_created` (when `kind == "task"`).
- `notification_created` (after the dispatcher processes the job).

Ordering and notification details:

- if an immediate task is created, `reminder_submit_response` is delivered
  before `new_task_created`
- task-kind at-time notifications use the task title as the notification title,
  not the generic `"Reminder"`
- task-kind at-time notifications use description:
  `Your task '<title>' is due now.`

### Server-initiated schedule events

- `new_task_created` – emitted whenever the activation/materialization service creates a task from an occurrence.
- Notification-related events described above fire as the dispatcher claims
  planned jobs.
- `occurrence_updated` – emitted after `occurrence_edit` with `apply_scope=single`.
- `occurrence_canceled` – emitted after `occurrence_cancel` with `apply_scope=single`.
- `occurrence_deleted` – emitted after `occurrence_delete` with `apply_scope=single`.
- `occurrence_series_updated` – emitted after `apply_scope=following|all` edit/cancel/delete mutations.

### `occurrences_fetch` (client → server)

Request a window of planner occurrences to draw repeating blocks without waiting
for the scheduler to materialize them in `tasks`.

```json
{
  "event": "occurrences_fetch",
  "data": {
    "start": "2025-01-01T00:00:00Z",
    "end": "2025-01-31T23:59:59Z"
  }
}
```

**Response:** `occurrences_list`

```json
{
  "event": "occurrences_list",
  "data": {
    "start": "2025-01-01T00:00:00Z",
    "end": "2025-01-31T23:59:59Z",
    "occurrences": [
      {
        "id": "<occurrence id>",
        "schedule_id": "<schedule id>",
        "user_id": "<user id>",
        "series_uuid": "<series uuid>",
        "instance_key": "20260222T112500",
        "occurs_at": "2025-01-02T10:00:00Z",
        "rev": 4,
        "source_rev": 4,
        "state": "planned|canceled",
        "snapshot": { "...": "..." },
        "overrides": { "...": "..." },
        "customized_fields": ["occurs_at"],
        "payload": { "...merged snapshot and overrides..." },
        "is_all_day": false,
        "all_day_span_days": 1
      },
      ...
    ]
  }
}
```

- `payload` is the merged runtime view (`snapshot` overlaid with `overrides`).
- Use `series_uuid` + `instance_key` as stable series identity; `occurrence_id` may change after regeneration.
- `occurrences_fetch` returns `planned` and `canceled` states; `deleted` occurrences are excluded.
- Requested `start/end` window is authoritative, including past occurrences.
- For soft-deleted schedules, only occurrences with `occurs_at <= server_now` are returned.

### `occurrence_edit` (client → server)

```json
{
  "event": "occurrence_edit",
  "data": {
    "schedule_id": "<schedule id>",
    "anchor_occurs_at": "2026-03-10T14:00:00Z",
    "changes": {
      "occurs_at": "2026-03-01T09:30:00Z",
      "title": "Moved standup",
      "show_before_minutes": 30
    },
    "apply_scope": "single" | "following" | "all",
    "include_customized": false
  }
}
```

- Target resolution:
  - If `occurrence_id` is present, it is used directly.
  - Otherwise, `schedule_id + anchor_occurs_at` is required; server materializes toward the anchor in repeated batches (500 occurrences per batch), resolves the planned instance, then applies scope.
- `single` edit can restore `canceled` occurrences to `planned`; `deleted` occurrences are not editable.
- `apply_mode` is accepted as a backward-compatible alias for `apply_scope`.
- `following` split truncates the old schedule at `min(anchor_occurrence, first_new_occurrence)-1s` to avoid overlap.
- `all` applies to future series segments from the anchor; schedules whose segment ended before the anchor are preserved unchanged.
- For `following|all`, if `changes` includes `occurs_at` and omits `rrule`, backend rewrites timing selectors in stored RRULE (`BYHOUR/BYMINUTE/BYSECOND`) by local wall-clock delta when those selectors are explicitly present.
- `include_customized=false` migrates customized rows to the new split schedule segment without selective merge.
- `include_customized=true` migrates customized rows and selectively merges non-customized keys from the new template.

### `occurrence_cancel` (client → server)

```json
{
  "event": "occurrence_cancel",
  "data": {
    "occurrence_id": "<occurrence id>",
    "apply_scope": "single" | "following" | "all",
    "include_customized": false,
    "reason": "optional text"
  }
}
```

- `single` marks only one occurrence canceled (idempotent if already canceled).
- `following` cancels from target forward.
- `all` cancels all planned occurrences in the series and deactivates schedules.
- `following|all` emit `occurrence_series_updated` with `action: "cancel"`.
- Target resolution matches `occurrence_edit`: `occurrence_id` first, otherwise `schedule_id + anchor_occurs_at` with repeated-batch materialization toward the anchor.
- Anchor lookup resolves planned rows; for already canceled/deleted targets use `occurrence_id`.

## Additional Notes for Client Implementers

- Multiple sessions for the same user receive broadcasts (except where noted).
  Use the `sid` from the `connected` payload to identify the active session.
- Large lists (`notifications_batch`, `tasks_refresher`) can be streamed; there
  is no pagination on task refresh events.
- All mutation handlers may return standard WebSocket close frames when an
  unhandled error occurs; reconnect logic should retry the `connect` flow.
- Maintain an idle timeout shorter than 60 s to ensure `pong` responses stay in
  flight, otherwise the backend will close the connection.
